# FAT/VFAT Support in Initramfs

## Findings

- `/dev/sda1`/`/dev/sda2` mounts failing with `mount -t vfat … No such device` point strongly to the initramfs missing FAT/VFAT support. The config discovery helper (`installer/runtime/lib/config_discovery.sh` and its initramfs mirror) always tries `mount -o ro -t vfat` before ext4, so SP_CONFIG being FAT32 means this path must succeed.
- The installer initramfs is assembled by `tools/build_installer_initramfs.sh`: it creates the `/bin`, `/runtime/lib`, and `/lib/modules` tree, stages a BusyBox binary (with `modprobe` among the `REQUIRED_APPLETS`), copies the runtime helpers (`runtime/lib/*.sh`), plants `/init` from `installer/init/init.sh`, and finally packs everything with `cpio`/`gzip`. Kernel modules are pulled from `${SP_INSTALLER_MODULES_ROOT}/${KERNEL_VERSION}` (defaulting to `build/runtime-chroot/lib/modules/<version>`), copied wholesale into `build/installer-initramfs/lib/modules/<version>`, but there is no `depmod` pass yet so `modules.dep`/`modules.alias` are missing.
- The initramfs entrypoint mirrors the runtime `installer/init/init.sh` tree: `sp_bootstrap` runs before `sp_run_installer`, mounts `/proc`/`/sys`/`/dev`, records module snapshots, and currently modprobes storage-related drivers (`virtio_blk`, `nvme`, `usb-storage`, etc.) before proceeding to `sp_discover_config`. `SP_STORAGE_MODPROBE_BIN` tracks the BusyBox `modprobe` if available. At no point does it proactively load filesystem modules such as `fat`/`vfat` or the `nls` helpers that `vfat` pulls in.
- BusyBox provides `/bin/modprobe` via the build script link farm and `init` already guards against a missing modprobe (logs `modprobe-unavailable`). That means we can log `[SP-INSTALLER]` messages for FAT/VFAT modprobe attempts and avoid hard failures even if the kernel already has them built-in.

## Plan

1. Extend `tools/build_installer_initramfs.sh` to confirm the FAT/VFAT/NLS modules exist in `${MODULES_SRC_DIR}` (falling back gracefully if the kernel has them built-in elsewhere) and to stage their `*.ko` files alongside the rest of `/lib/modules`. After the copy we should run `depmod -b "${INITRD_ROOT}" "${KERNEL_VERSION}"` so the initramfs tree contains `modules.dep`/`modules.alias`, enabling `modprobe fat` and `modprobe vfat` to resolve dependencies.
2. Update `installer/init/init.sh` (and keep `build/installer-initramfs/init` in sync) to load FAT/VFAT support early in `sp_bootstrap`, ideally right after the storage driver probes. Introduce a helper such as `sp_load_fat_modules` that tries `modprobe fat`, `modprobe vfat`, `modprobe nls_cp437`, and `modprobe nls_iso8859-1`, logging `[SP-INSTALLER] fat-support=modprobe module=… rc=…` for diagnostics but never aborting if the applet or modules are absent. This ensures the later FAT32 mounts in `sp_discover_config` see the right filesystem support even on modular kernels.
3. Add a short note to `docs/CONFIG_DISCOVERY.md` reminding readers that `SP_CONFIG` is FAT32 and that the initramfs now loads the `fat`/`vfat` modules early so config discovery can mount it deterministically.
4. Create/extend tests (e.g., augment `tests/installer/test_installer_initrd.py` or a new `tests/installer/test_init_modprobe.py`) that build the initramfs via `tools/build_installer_initramfs.sh`, extract `build/installer-initramfs/init`, and assert the new `modprobe fat`/`modprobe vfat` lines exist so future changes cannot remove the early loads.
5. Run `pytest tests/installer/test_config_discovery_busybox.py` (per Block C requirements) and keep `make ci-smoke`/other verification notes updated if feasible; record the `depmod`/`modprobe` expectation in the analysis doc along with any test output.
